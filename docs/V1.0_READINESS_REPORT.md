# Forge CLI v1.0 readiness report

## Executive assessment

Forge has a strong v0.99 baseline and now contains the principal foundations requested for a v1.0 candidate: a TypeScript supervisor with exclusive filesystem and process authority, a bounded Python worker, a versioned JSONL protocol, explicit approval gates, provider presets, MCP and ACP boundaries, optional Daytona support, visible checklists, long-horizon compaction, bounded repair escalation, redacted audits, and a 5,000-word Constitution. The current working tree also includes targeted v1.0 hardening and documentation updates.

A responsible release decision must distinguish **implemented**, **locally verified**, **externally integration-tested**, and **not proven**. The repository’s automated tests can demonstrate many local invariants, but they cannot prove that every provider account, model, MCP server, remote Daytona deployment, operating system, shell, filesystem race, or undiscovered vulnerability behaves safely. In particular, no serious audit can establish that Forge is free of zero-day vulnerabilities. The release claim should therefore be that Forge passes its documented checks and preserves its documented boundaries, not that it is perfect or zero-day-free.

## Audit work completed

The complete tracked project snapshot was assembled for independent review, including TypeScript, Python, protocol files, tests, manifests, and documentation. Generated artifacts and the long historical optimization brief were excluded to keep the review focused on maintained source. A live model catalog was fetched before selecting review models, and the catalog was not hardcoded into Forge because provider catalogs change.

One independent Gemini review completed far enough to identify hypotheses around ACP input buffering, possible path-validation races, and ACP memory bounds. The ACP buffering hypothesis was confirmed locally: the original CLI implementation accumulated all standard input before checking limits. Forge now processes ACP input incrementally with a one-million-byte total cap, a 200-request cap, bounded JSONL lines through the bridge, and explicit failure on limit exhaustion. A process-level regression test exercises the oversized-input path.

The path-validation race observation remains a hypothesis rather than a confirmed exploit. Forge performs relative-path, normalization, sensitive-name, and component-level symbolic-link checks before filesystem operations, and the regression suite covers ordinary symlink escapes. A future hardening pass should consider platform-specific race-resistant primitives or directory-handle techniques, but no new primitive should be introduced casually because it must preserve cross-platform behavior and transactional rollback.

Additional independent model calls were attempted with GPT-5, Claude Sonnet 4.6, and Gemini 3 Flash. Those calls could not complete the full snapshot review in the current execution environment. The repository records this limitation in `V1.0_MODEL_AUDIT_NOTES.md`. The result is useful evidence about one completed review and one confirmed local fix, but it is not a substitute for a complete multi-model audit.

## Provider and connectivity recommendations

Forge now supports multiple OpenAI-compatible provider routes through environment-driven configuration. This is a good v1.0 foundation because it gives users choice without adding provider credentials to protocol messages. The generic route is particularly important: users can select a compatible gateway or self-hosted endpoint without waiting for a bespoke adapter.

The provider layer should not claim universal compatibility. Providers differ in model IDs, tool-call behavior, streaming details, token parameter names, rate limits, context windows, and unsupported request fields. Groq’s official documentation, for example, describes its OpenAI compatibility as “mostly compatible” and lists unsupported fields. Google documents its own OpenAI-compatible Gemini endpoint and model selection. OpenRouter documents its compatible chat-completions path and attribution headers. xAI documents OpenAI REST compatibility and Bearer authentication. Forge’s minimal request shape is intentionally conservative, but each live provider should be validated through a user-controlled integration test before a provider-specific feature is called stable [1] [2] [3] [4].

Before a final v1.0 declaration, add a documented provider smoke matrix that users can run with their own credentials. The matrix should test authentication failure, a minimal text completion, a bounded tool proposal, malformed tool arguments, streaming if enabled, timeout behavior, and provider-specific unsupported fields. It should never print the key. The matrix should report the provider, endpoint host, selected model, request class, and redacted result category.

## MCP and connectivity recommendations

The current MCP design is appropriately conservative. Servers are disabled by default, local stdio is bounded, child environments are minimized, request and response paths are limited, and tool calls remain subject to Forge policy and approval. This should remain the v1.0 default. “All MCPs work well” cannot mean that Forge guarantees every third-party server; it can mean that Forge handles valid compatible servers predictably and handles malformed, slow, oversized, or disabled servers safely.

Before release, test representative MCP servers or fixtures that exercise initialization, tool discovery, a successful call, a server error, malformed JSON, an oversized response, stderr flooding, process exit, cancellation, and repeated start/close cycles. Add a child-process leak check on supported platforms. Keep remote MCP disabled unless a separate design introduces provenance, authentication, consent, and data-flow controls strong enough for remote operation.

ACP should be documented as a local adaptation boundary rather than a complete editor protocol implementation. The streaming byte cap fixed a concrete risk, but interoperability still requires fixture testing against the clients Forge intends to support. The process-level test must remain so future refactors cannot reintroduce whole-stdin accumulation.

## Dependency and maintenance recommendations

The current dependency audit reports no known vulnerabilities. `npm outdated` shows newer major versions of `@types/node` and TypeScript than the versions currently accepted by the project. A newer major version should not be adopted solely because it is newer. Before upgrading, run the full matrix against Node 22, inspect TypeScript release notes for NodeNext and strictness changes, update lockfiles deterministically, and compare generated output. Pinning a tested major range and documenting the supported runtime is safer than chasing every latest release.

The Python package should receive an equivalent dependency review using the project’s chosen audit tooling in release automation. The wheel build is already part of the release gate; an explicit dependency vulnerability check and an installation test in a clean virtual environment would improve confidence. The release process should also verify that generated `egg-info`, build directories, and wheel artifacts are not accidentally committed.

## UX and efficiency recommendations

The TUI status bar and checklist make the current stage more legible, while simple output remains suitable for pipes and logs. The next usability pass should test narrow terminals, redirected output, non-UTF-8 bytes, long session IDs, long labels, approval denial, cancellation, and provider failure. Add a `--quiet` or event-filter mode only if it can preserve the safety-critical approval and failure lines; do not hide important risk information for the sake of visual compactness.

Efficiency work should remain evidence-based. Measure startup, context collection, provider request count, serialized context size, memory-sensitive ACP input, and representative long-horizon runs. Use reuse and pruning before lowering verification coverage. Report skipped roles, compaction, output truncation, retries, and budget exhaustion in the existing bounded telemetry. Avoid unsupported claims of multiplicative quality gains.

## Release decision recommendation

Forge should not be described as “perfect” or “zero-day safe.” The current local release gate now passes: formatting, strict TypeScript typecheck, build, 46 Node tests, 19 Python tests, Python wheel construction, `npm audit --audit-level=moderate` with zero reported vulnerabilities, Python compilation, whitespace checks, direct CLI smoke checks, normal ACP JSONL handling, and oversized ACP rejection. It can therefore be described as a strong v1.0 release candidate, while the maintainers either complete or explicitly defer the recommendations above. The most important pre-release blockers are not additional decorative features; they are repeatable provider smoke tests, representative MCP fixtures, clean-environment Python dependency auditing, multi-platform terminal checks, and a second independent review pass when review capacity is available.

The practical declaration for this working tree is **v1.0 release candidate**, not final v1.0. Final v1.0 should additionally require the full local regression suite, strict typecheck, build, formatting, dependency audits, clean-clone installation, protocol fuzz/bound tests, provider configuration tests, MCP/ACP fixtures, a reviewed Constitution, and a written limitations section. Live provider and Daytona checks must remain user-controlled because no credentials were supplied. That standard protects the credibility of the version number while allowing users to benefit from the implemented capabilities.
