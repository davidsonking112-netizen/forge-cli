# Forge CLI v0.9 Master Optimization Prompt

## Mission

You are the principal engineer responsible for planning, implementing, testing, documenting, and publishing Forge CLI v0.9 in the private repository `davidsonking112-netizen/forge-cli`. Treat this document as the governing implementation brief for the entire release. Your objective is not to add a handful of isolated features. Your objective is to optimize Forge CLI as a coherent, local-first AI coding-agent product: safer, clearer, faster, more reliable, easier to review, more reproducible, and more maintainable without weakening the core trust model.

Forge is a lightweight coding-agent CLI built deliberately from **Node.js, strict TypeScript, and Python**. The TypeScript supervisor is the sole authority over the filesystem, processes, workspace containment, approvals, integrations, sessions, checkpoints, and user-facing execution. The Python worker is untrusted orchestration and provider-bound reasoning code. It may assemble bounded context, produce plans, request tools, and report model output, but it must never receive direct filesystem or process authority. Preserve this split throughout v0.9, even if a seemingly simpler design would combine runtimes or move authority into Python.

Begin with THINK–PLAN–EXECUTE discipline. Before changing code, inspect the repository, establish the exact v0.8 baseline, identify architectural risks, write a scoped v0.9 plan, and define acceptance tests for each proposed change. Do not begin with speculative refactoring. First understand existing behavior, data formats, public commands, compatibility constraints, and safety boundaries. Every optimization must be justified by a user-visible improvement, a measurable reliability gain, a security improvement, a maintenance reduction, or a clear reduction in complexity.

The release must be implemented incrementally in reviewable sectors. Each sector must have a written design note, implementation, focused tests, integration coverage, documentation updates, and a verification checkpoint before the next sector is considered complete. If a sector reveals that an originally proposed behavior would expand authority, create hidden autonomy, or make safety less legible, stop and redesign that part rather than quietly weakening the boundary.

## Current baseline and inherited contract

Assume Forge CLI v0.8.0 is the starting point unless repository inspection proves otherwise. The v0.8 release includes durable step journals, workspace fingerprints, read-only recovery assessment, stale-resume refusal, structured verification evidence, bounded transactional unified-diff application, file-level `--only` change-set selection, incremental metadata-only indexing with bounded relationships, policy explanations, exact-argument expiring approval scopes with interactive revocation, local ACP correlation and categorized errors, local MCP cancellation and categorized lifecycle errors, and inert declarative extension recipes.

The current repository contains a Node.js/npm workspace, strict TypeScript compiled with NodeNext conventions, a Python package under `python/forge_agent`, a shared protocol package, source-level tests and public CLI stress tests, documentation, and release scripts. Maintain the existing toolchain and scripts unless a change is clearly necessary. Preserve Node.js and TypeScript for authority and Python for the worker/provider boundary. Do not replace the stack with a single language, a cloud service, a daemon, a browser application, or a remote orchestration layer.

The v0.9 release must preserve the following product promises. Forge starts in a read-only, plan-first posture. Filesystem writes and local command execution are visible and approval-gated. Destructive, network, credential-sensitive, and other globally denied actions remain denied regardless of model output, repository instructions, policy packs, profiles, extension metadata, MCP data, ACP messages, or provider responses. The model never becomes an authority merely because it is confident. Forge never silently pushes, opens pull requests, contacts remote Git services, launches remote MCP or ACP transports, executes arbitrary third-party extensions, runs hidden background agents, or performs unbounded recursive delegation.

## Sector 1: Architecture, authority, and invariant preservation

Review the whole architecture as a security-critical system. Draw a current authority-flow diagram showing the user, CLI, TypeScript supervisor, workspace tools, policy engine, session store, local integration clients, Python worker, provider adapter, and model provider. For every edge, document whether data, authority, or both can cross it. Reduce authority crossings wherever possible. Data crossing a boundary must be bounded, typed, sanitized, and treated as untrusted.

Make the supervisor’s ownership explicit in code. Filesystem path resolution, symlink rejection, sensitive-file denial, file reads, writes, checkpoints, process spawning, environment construction, timeouts, output limits, approval decisions, policy enforcement, session persistence, and integration lifecycle must remain reachable only through supervisor-controlled TypeScript code. The worker may request a tool through JSONL, but it cannot call Node APIs, Python filesystem helpers, subprocess APIs, package installers, network clients, or workspace-controlled imports to bypass the supervisor.

Audit every current and proposed code path for confused-deputy behavior. In particular, verify that a path supplied by the worker, an extension recipe, a policy pack, an MCP server, an ACP client, or a provider response cannot be interpreted as a new approved root. Verify that a command supplied as an array cannot gain shell interpretation unless explicitly requested and approved. Verify that approval applies to the actual normalized operation, not merely to a human-readable summary. Verify that a stale fingerprint, stale diff, stale checkpoint, stale verification result, or expired approval cannot be silently treated as current.

Introduce a concise internal authority matrix. It should identify each operation, its risk class, its responsible module, whether approval is required, whether it is globally denied, what bounds apply, what is persisted, and what evidence is produced. Add tests that fail if a new tool is added without explicit metadata, risk classification, policy treatment, approval handling, and protocol representation. Prefer deny-by-default registration: an unknown tool, event, integration capability, recipe field, or policy field must not become executable through structural coincidence.

## Sector 2: CLI and terminal user experience

Optimize the CLI around clarity under pressure. A user should be able to understand what Forge is doing, what it intends to do, what it needs approval for, what changed, what was verified, and what remains unresolved without reading raw JSON. Improve text rendering, simple line mode, full-screen TUI mode, and JSON output as coordinated representations of the same typed events. Do not make the TUI the only way to access important safety information; every meaningful operation must have a deterministic non-interactive representation suitable for scripts and CI.

Define a consistent command taxonomy. Read-only inspection commands should be obvious and safe to run. Mutating commands should advertise their approval requirement and preview their exact operation before execution. Recovery commands should distinguish assessment from action. Verification commands should distinguish recorded evidence from a newly requested check. Integration commands should distinguish configuration validation, capability discovery, explicit enablement, invocation, cancellation, and shutdown.

Improve help output, error messages, exit codes, and examples. Every command must have a concise usage line, a description of whether it reads, writes, executes, or merely assesses, and a predictable exit-code policy. Errors should state the denied or failed operation, the safety reason, whether retrying is meaningful, and the safe next action. Do not leak provider credentials, raw environment values, secret-looking command arguments, or unrestricted third-party error bodies in diagnostics.

Add machine-readable output fields for decision, reason, risk, selected scope, stale status, correlation ID, checkpoint, verification status, and next safe action where relevant. Preserve stable field names and document them. Human output can be friendly, but JSON output must not depend on terminal width, color, timing, or incidental ordering. Add snapshot-like tests for representative text and JSON output while avoiding brittle timestamps and random identifiers.

Optimize interactive approval. A user should be able to see the normalized tool name, risk class, reason, target paths, command and arguments, expected effects, scope, expiry, and whether the operation is reversible. Session approval must never be described as “allow everything.” Provide explicit options to approve once, approve a narrowly described session scope, deny, cancel the active operation, and revoke an existing in-memory scope. Make the difference between denial by user, denial by policy, cancellation, and execution failure visible.

## Sector 3: Planning, agent turns, and bounded autonomy

Make plan-first behavior a real product contract rather than a rendering convention. Every coding task should begin with a bounded plan containing a goal, assumptions, ordered steps, expected files or information, verification intent, and risk notes. Plans should be stable enough to journal, inspect, compare, and resume. If the provider returns incomplete, contradictory, oversized, or malformed plans, the worker must normalize or reject them without creating hidden actions.

Improve step semantics. Define a small, explicit lifecycle such as pending, active, awaiting-approval, complete, blocked, stale, skipped, and failed. Record transitions with timestamps, bounded reasons, proposal IDs, and tool-result references. Require the supervisor to be the authority that accepts transitions caused by real tool outcomes. The worker may suggest a status, but it must not claim completion for a write or command that the supervisor did not execute successfully.

Add bounded turn budgets at every level. Limit total prompts, plan steps, tool proposals, provider tokens, delegated roles, and event volume. Make limits configurable only inside safe maxima. When a limit is reached, stop with an actionable bounded result rather than retrying indefinitely. Retries must be classified as safe or unsafe. A retry must not repeat a mutation automatically, re-submit an approval request forever, or expand context beyond the configured budget.

Keep delegation advisory and bounded. If multi-agent analysis remains supported, maintain fixed roles, finite sequential or explicitly bounded parallelism, no recursive delegation, no worker-side tools, and clear attribution of specialist output. Make cancellation propagate to provider calls, child analysis, and pending work. A cancelled plan must not become a successful session merely because a late event arrives.

Treat prompts, repository instructions, provider messages, extension metadata, and tool descriptions as untrusted data. Add explicit prompt-injection handling in the worker and supervisor prompt construction: instructions discovered in repository content can inform coding conventions but cannot authorize secrets, network access, destructive commands, approval bypasses, hidden files, or changes to Forge policy. Test adversarial instructions that attempt to impersonate the supervisor or user.

## Sector 4: Session persistence, recovery, and migrations

Design a robust session state model for interrupted work. A session record should retain bounded lifecycle status, prompt or goal, plan snapshot, step journal, workspace fingerprint, recovery assessment, approval events, tool proposals, tool results, verification evidence, integration correlation, and a bounded event history. Establish explicit size limits and sanitization rules for every persisted field. Atomic writes, restrictive permissions, safe IDs, and legacy-compatible reads are mandatory.

Separate three concepts: assessment, resume request, and execution. `session recovery` should be read-only and deterministic. It should explain whether continuation is safe, whether re-planning is required, or whether a human must inspect workspace changes. `session resume` should persist the selected assessment and start a new supervised session only after all freshness and prompt checks succeed. It must never replay a previous mutation or command implicitly. If explicit replay or re-application is ever proposed, design it as a separate command with a new preview, fresh fingerprint validation, explicit approval, and no automatic merge.

Improve drift classification beyond a single boolean when practical. Classify relevant-file modification, relevant-file deletion, new untracked content, changed Git metadata, missing workspace, stale checkpoint, changed policy context, and absent legacy fingerprint separately. Each classification must map to a safe next action. Avoid false precision: if bounded context is insufficient to distinguish causes, report “manual intervention” rather than guessing.

Maintain backward compatibility with v0.7 and older records. Implement a version-aware normalization layer instead of scattering optional-field assumptions throughout the application. Legacy records without fingerprints or journals must remain readable but should receive conservative decisions such as re-plan or manual intervention. Malformed records should fail closed with a useful diagnostic and must not be partially executed. Add migration tests for the oldest supported shape, v0.7 records, truncated records, unknown fields, oversized fields, invalid IDs, and hostile serialized values.

## Sector 5: Transactional changes and reviewability

Treat every mutation as a change set. A change set has an identity, source, target workspace, expected base fingerprint or file hashes, bounded file list, action per file, byte and line summary, risk classification, review decisions, approval record, checkpoint identity, application outcome, and rollback outcome. The system should make it difficult to approve one description and execute another.

Improve read-only diff review. Provide deterministic file-level entries for create, modify, delete, and rename actions. Include normalized paths, current hash, expected hash where available, bytes before and after, hunk counts, additions, deletions, conflict reason, selected state, and an overall change-set digest. Ensure the digest is stable for the same diff and workspace base. Keep preview read-only and bounded.

Support explicit per-file selection without pretending that selection is a merge engine. The user must be able to inspect the full proposed set, choose a bounded subset, and see exactly which files are excluded. Applying a subset must validate only the selected change set against current files while still rejecting unsafe paths and malformed patches. The application must remain transactional: validate every selected file before the first write, create a checkpoint manifest and backups, apply all selected changes, and restore the checkpoint if any write fails. No partial success may be reported as success.

Do not implement automatic three-way merge, rebase, conflict guessing, or conflict suppression unless separately approved. A stale context should produce a clear conflict and require a new review. Rename handling, delete handling, new-file creation, trailing-newline semantics, duplicate targets, binary content, symlink components, and sensitive names require dedicated tests.

Make checkpoint recovery safer. Checkpoint manifests must be workspace-bound, path-contained, size-bounded, integrity-checked, and resistant to path manipulation. Restoration should report each restored, removed, skipped, or failed path. Never restore a checkpoint into a different workspace. Consider expiry or bounded cleanup for old checkpoints, but never delete an active or recently referenced recovery artifact without a clear retention policy.

## Sector 6: Verification and reproducibility

Make verification a first-class evidence pipeline. A verification record should identify the command or check definition, normalized arguments, workspace, start and finish times, duration, exit code, bounded output, truncation state, status, environment policy summary, workspace fingerprint, and relationship to the plan step or change-set digest. Do not persist secrets or unrestricted environments.

Distinguish `not-run`, `blocked`, `passed`, `failed`, `timed-out`, `cancelled`, and `stale`. A check is passed only when the supervisor actually ran the approved command and the result satisfies the defined criterion. A model’s claim, a cached result with no matching fingerprint, or a command that was denied cannot be passed evidence. If a workspace or relevant policy has changed, mark affected evidence stale rather than silently trusting it.

Keep `forge verify` evidence-only by default. It should explain what was recorded, whether it is current, and why it is stale or incomplete. If v0.9 adds an explicit rerun mode, it must be visibly distinct, preview the commands, require approval for execution, use fresh bounds, create new evidence records, and never overwrite historical evidence. Add reproducibility metadata such as tool version, protocol version, command digest, workspace fingerprint, and selected environment policy without recording secrets.

Support deterministic verification plans. Derive candidate checks from bounded project metadata, extension recipe metadata, and the agent plan, but never execute a recipe or inferred command without the same supervisor approval and policy treatment as any other process. Validate command arrays, reject shell metacharacter tricks where shell mode is not explicitly allowed, enforce time/output bounds, and stop after the configured maximum number of checks.

## Sector 7: Repository context and local relationships

Optimize context selection for usefulness, determinism, privacy, and bounded cost. The context collector should respect approved-root containment, ignored/generated directories, sensitive-file exclusions, `.gitignore` rules, file-count and byte bounds, and relevant-file ranking. Explain why a file was selected. Avoid automatically sending the entire repository to a provider.

Improve the opt-in local index without turning it into a hidden semantic database. Store only bounded metadata such as normalized path, size, modification signature, symbol names, language or file class, and relationship edges. Do not persist file contents, credentials, provider prompts, or unrestricted embeddings. Make index creation, update, query, and clearing explicit user actions with restrictive permissions and bounded output.

Expand relationships carefully. Support dependency edges from bounded relative imports, source-to-test association based on conservative naming and path rules, configuration/dependency-neighbor edges, and perhaps changed-file-to-test candidates. Every edge must have a kind, source, target, derivation reason, and bounded confidence or certainty where useful. Unknown or ambiguous relationships must be omitted or labeled as candidates, not presented as facts. Never execute an imported path or use relationship data to authorize a tool.

Make incremental indexing correct under file creation, deletion, rename, timestamp granularity, clock changes, and partial scans. Use content hashes only when reading bounded text is already permitted for indexing; never treat modification time alone as proof of identity when a collision or clock issue could produce incorrect relationships. Test index corruption, size limits, legacy versions, duplicate edges, malicious paths, symlink directories, and interrupted writes.

## Sector 8: Policy, profiles, and approval scopes

Review the policy engine as an immutable ceiling plus restrictive overlays. The global ceiling must be expressed in code and tests, not merely documentation. Policy packs and autonomy profiles may deny more risk or tools but may never allow a globally denied action, broaden a workspace root, enable network by implication, authorize credentials, or disable approval for a dangerous class.

Improve policy explanations. For every requested operation, show the risk classification, global decision, profile restriction, policy-pack restriction, approval requirement, exact final decision, and safe alternative if denied. Avoid ambiguous terms such as “safe” when the operation is merely allowed under a narrow policy. Ensure explanations never expose sensitive arguments or provider credentials.

Make approval scopes useful without making them broad. Each session scope should contain the tool, exact canonical argument digest, bounded human summary, expiry, and optional bounded path descriptions. A scope must not match a different tool, argument set, workspace, policy context, or change-set digest. Scope expiration must be checked at use time, not only creation time. Revocation must clear the active in-memory scope immediately and create an auditable event. Do not persist approval scopes as reusable global grants.

Consider adding a non-interactive approval-plan mode that prints pending approvals and exits without executing them. This can improve CI and review workflows while preserving safety. If implemented, ensure it cannot be confused with approval. A plan file must be treated as untrusted input, validated against the actual proposal digest, and rejected if the workspace, policy, tool, arguments, or expiry differ.

## Sector 9: ACP and MCP local integration hardening

Keep ACP and MCP local-only. Do not add remote URLs, network transports, marketplace discovery, automatic server downloads, or persistent implicit enablement. All configured external processes remain untrusted. Configuration validation must never launch a child.

Harden ACP JSONL handling. Enforce maximum line size, request count, method length, parameter shape, ID type, and response size. Preserve request correlation IDs in normalized responses and internal events. Categorize parse errors, invalid requests, invalid parameters, unsupported events, cancellation, and lifecycle failures. Ensure one malformed request cannot corrupt state or make later requests bypass validation. Add fixtures for malformed JSON, null IDs where forbidden, duplicate IDs, oversized lines, unknown methods, malformed arrays, cancellation, and request ordering.

Harden MCP lifecycle handling. Validate command and argument shapes before spawning. Use a minimal child environment and no implicit shell. Drain stderr without treating it as protocol output. Bound stdout and individual lines. Track initialization, capability discovery, active calls, cancellation, close, process error, process exit, timeout, malformed response, and server error as distinct states. Correlate every response by request ID. AbortSignal cancellation must reject the caller, send a bounded cancellation notification where supported, clean up timers/listeners, and prevent late responses from resolving a cancelled call.

Never let an MCP tool descriptor become a Forge filesystem or process capability automatically. MCP calls remain an explicitly invoked integration action with their own approval and policy treatment. Normalize or redact child errors before exposing them. Add deterministic child fixtures rather than relying on external servers.

## Sector 10: Declarative extension recipes

Keep extension manifests metadata-only. A manifest may declare identity, protocol compatibility, capabilities, bounded context globs, verification command arrays, display metadata, and other explicitly approved inert fields. It must not contain executable JavaScript, Python, shell snippets, module paths, dynamic imports, lifecycle hooks, callbacks, remote URLs, credential requests, or arbitrary tool definitions.

Improve recipe inspection rather than recipe execution. Provide users with a safe view of what a recipe would suggest, which paths it might select, which checks it describes, what bounds apply, and why Forge will not execute it automatically. If a user explicitly chooses a recipe-derived check, convert it into a normal supervisor proposal that is independently validated, policy-checked, bounded, and approval-gated. The recipe itself must never be trusted merely because it came from a manifest.

Validate recipe arrays for maximum count, maximum argument length, safe path-like fields, forbidden shell control characters where applicable, duplicate commands, and unsupported tools. Treat unknown manifest keys conservatively. Add tests proving that manifest content cannot load a module, run a command, alter the approved workspace, lower policy, or modify the supervisor’s environment.

## Sector 11: Python worker and provider boundary

Audit the Python worker for import isolation, filesystem assumptions, process assumptions, provider error handling, token bounds, retries, cancellation, and event normalization. The worker must run from a controlled module path rather than allowing workspace files to shadow `forge_agent` modules. It must not inherit unrestricted environment variables or expose credentials in events.

Keep provider adapters behind a narrow interface. Provider mode must normalize model responses into the same plan, text, proposal, result, delegation, error, and completion event types used by the mock mode. Malformed provider tool calls must become bounded errors or denied proposals, never arbitrary Python calls. Provider retries must have finite counts, backoff bounds, cancellation, and redaction.

Make mock mode a strong deterministic test oracle. It should exercise read-only inspection, approval-gated mutation, verification evidence, cancellation, stale recovery metadata, and bounded failure behavior without network access. Avoid hardcoding tests only around model text; test protocol events and supervisor state transitions.

## Sector 12: Reliability, performance, and resource control

Measure startup time, context collection time, index build time, worker startup, first plan latency, preview latency, approval latency, verification duration, memory behavior, and maximum event volume. Set realistic local bounds and document them. Optimize only after measuring. Prefer streaming and incremental processing over loading unbounded files or outputs.

Audit every asynchronous lifecycle for leaks: child processes, readline interfaces, timers, AbortSignal listeners, stdout buffers, stderr streams, pending protocol promises, TUI alternate screens, temporary files, and checkpoint artifacts. Ensure cancellation and errors release resources. Late events must be ignored or classified rather than mutating completed state.

Use deterministic ordering for files, relationships, events where ordering is not semantically time-dependent, JSON output, and query results. Avoid nondeterministic tests based on exact timestamps or process scheduling. Make random IDs injectable or testable where useful without weakening production uniqueness.

Do not introduce background daemons, recurring jobs, automatic repository watchers, cloud queues, or hidden persistence as an optimization. Local-first means predictable local execution, not invisible long-running infrastructure.

## Sector 13: Security, privacy, and adversarial testing

Perform a focused threat-model review for path traversal, symlink races, sensitive filenames, environment leakage, command injection, shell expansion, workspace confusion, policy downgrade, approval replay, stale-record replay, malformed JSONL, child-process escape, provider prompt injection, extension execution, MCP capability confusion, log injection, oversized inputs, denial of service, and unauthorized remote access.

Strengthen path safety without claiming impossible race-free guarantees if the design does not provide them. Reject absolute paths, traversal components, NUL bytes, sensitive credential-like names, and symlink path components. Validate both old and new paths for rename operations. Verify checkpoint restoration paths independently. Avoid following symlink directories during collection and indexing.

Sanitize persisted and displayed values. Redact API keys, tokens, passwords, bearer values, private-key-like strings, and common secret assignments in command arguments, provider errors, MCP errors, session events, and diagnostics. Keep enough structured information to debug without storing secret payloads. Test secrets in nested objects, arrays, shell-like strings, JSON strings, and multiline outputs.

Add adversarial fixtures authored specifically for Forge. Include repository instructions that say to ignore policy, fake approval text, request `.env` contents, invoke a remote server, run a destructive command, load a Python module from the workspace, or modify Forge state. The expected result must be safe refusal or untrusted-data treatment.

## Sector 14: Protocol and data-contract quality

Treat the shared TypeScript protocol types and documentary JSON schema as a compatibility surface. Every new event field needs a clear optional/required decision, bounds, sanitization behavior, and test coverage. Update the Python worker, TypeScript supervisor, schema, protocol README, session normalization, renderers, and tests together.

Use explicit discriminated unions for event types, risk classes, verification statuses, recovery decisions, integration errors, and relationship kinds. Reject invalid protocol envelopes, unknown required semantics, oversized values, invalid timestamps where validation is expected, and mismatched session IDs. Do not rely on TypeScript compile-time types alone when receiving JSON from Python, providers, ACP, MCP, files, or child processes.

Document which fields are advisory, which are supervisor-authored, which are evidence, and which are user decisions. A worker-reported status is not the same as a supervisor-observed tool result. An MCP capability is not a Forge capability. A recipe suggestion is not an execution request. A recorded verification result is not a current verification result after workspace drift.

Create a v0.9 test matrix before implementation. It must cover unit tests for parsers, validators, policy decisions, path containment, fingerprinting, journal migration, relationship extraction, diff selection, checkpoint restoration, approval expiry and revocation, ACP errors, MCP cancellation, extension manifests, and redaction. It must cover Node integration tests for public commands and supervisor behavior. It must cover Python tests for worker protocol handling, provider normalization, cancellation, bounded output, and isolation.

Maintain regression coverage for every feature from v0.1 through v0.8. Do not delete historical tests merely because an implementation changed. If a behavior is intentionally changed, document the migration and update the test to assert the new safety-preserving contract. Add stress cases involving malformed numbers, oversized strings, duplicate protocol IDs, huge arrays, invalid Unicode or NUL input, missing files, changed mtimes, deleted paths, stale fingerprints, and unexpected child exits.

Use deterministic fuzzing for parsers, numeric bounds, JSONL messages, diffs, policy packs, manifests, and relationship inputs. A fuzz case may be accepted, rejected, or classified, but it must not crash the process, escape bounds, hang indefinitely, write outside the approved workspace, launch an unexpected child, or expose secrets. Keep the harness reproducible with a fixed seed and record the case count.

Run formatting, strict typechecking, production build, Node tests, Python tests, release checks, `git diff --check`, package audit, CLI smoke tests, and wheel builds. Add a fresh-clone verification that uses only tracked files, installs dependencies cleanly, runs all release checks, exercises version/help/public commands, and ends with a clean Git status. If any gate fails, diagnose and fix the cause rather than weakening the gate.

Update README, changelog, architecture, security, protocol, command help, and any schema or migration notes only after behavior is stable. Documentation must describe shipped behavior, not aspirations. State important limitations prominently: no automatic mutation replay, no automatic three-way merge, no remote MCP/ACP, no executable extensions, no hidden background agents, no automatic push or pull request, no blanket approval, no default semantic cloud index, and no silent verification reruns.

## Sector 17: Required implementation workflow

Follow this sequence unless a written plan update explains a safer alternative. First inspect the current repository status, branch, remote SHA, version metadata, tests, scripts, and v0.8 implementation. Second write the v0.9 plan with sector dependencies, risk ranking, acceptance criteria, and explicit non-goals. Third implement the highest-value safety and reliability improvements in small changes. Fourth run focused tests after every sector. Fifth perform a cross-sector review for authority leaks, compatibility breaks, misleading output, and unbounded behavior. Sixth update protocol/schema/docs/version metadata. Seventh run the complete release matrix, fuzz harnesses, direct CLI smokes, audit, and fresh-clone verification. Eighth commit and publish only after all gates pass.

At every step, report what was inspected, what changed, which tests were added or run, and what remains intentionally unsupported. Never state that a feature is complete merely because code compiles. A complete feature has implementation, bounded behavior, safety analysis, tests, documentation, migration treatment where applicable, and verification in a fresh clone.

## Definition of done

Forge CLI v0.9 is done only when all of the following are true. The TypeScript supervisor remains the only filesystem/process authority. Python, providers, ACP, MCP, recipes, repository content, policy packs, and model responses remain untrusted data sources or bounded proposal sources. Read-only and plan-first behavior remain the default. All writes and local commands remain approval-gated, bounded, visible, and checkpointed where mutation is transactional. Globally denied risks remain denied under every profile and configuration.

Session recovery is deterministic, step-aware, legacy-compatible, fingerprint-aware, and never implicitly replays mutations or commands. Change-set review is file-level, digestable, stale-aware, selectable, approval-gated, and all-or-rollback, with no automatic three-way merge. Verification evidence is typed, reproducible, bounded, stale-aware, and never silently rerun. Repository relationships are bounded metadata only and cannot grant authority. Approval scopes are exact-argument, expiring, path-described, revocable, and non-persistent as blanket grants. ACP and MCP are local-only, correlated, bounded, cancellable, categorized, and unable to expand Forge capabilities. Extension recipes remain declarative and inert unless converted into normal independently validated proposals.

The CLI is understandable in human and JSON modes. The protocol and schema are synchronized. Session and index migrations are safe. Node, TypeScript, and Python remain first-class maintained runtimes. Unit, integration, stress, adversarial, deterministic fuzz, release, audit, and fresh-clone checks pass. Documentation makes both capabilities and limitations clear. The main branch is clean and the published commit is independently verified.

## Explicit non-goals for v0.9 unless separately approved

Do not add remote MCP or ACP transport. Do not add automatic pushes, pull requests, remote Git mutation, or cloud repository synchronization. Do not add executable plugins, arbitrary extension modules, marketplace downloads, dynamic code loading, or recipe execution. Do not add hidden daemons, background watchers, recurring agents, unattended mutation, recursive delegation, unrestricted browser or network tools, blanket approvals, permanent approval grants, automatic three-way merge or rebase, or default cloud semantic indexing. Do not weaken secret filtering, environment minimization, output limits, timeouts, approved-root containment, symlink checks, process authority separation, or global deny rules for convenience.

If an optimization conflicts with these non-goals, the non-goal wins. If a proposed feature cannot be made safe, bounded, inspectable, and testable within the v0.9 release, defer it with a documented rationale rather than shipping an ambiguous partial implementation.

## Final instruction

Optimize Forge CLI as if every boundary will be audited by a security engineer, every command will be used in a damaged or partially modified repository, every provider response may be adversarial, every child process may fail, every user approval must be meaningful, and every release claim must be independently reproducible. Favor explicitness over magic, reversible operations over irreversible operations, local evidence over model assertions, narrow scopes over broad permissions, deterministic behavior over clever heuristics, and a smaller trustworthy product over a larger opaque one. Deliver v0.9 as a disciplined evolution of Forge, not as a replacement of its safety model.
